# token 用量优化

微信场景的特点是「**消息短、次数多、还要长期记忆**」，而成本恰恰死在"次数多"和"记忆全塞进上下文"上。
下面每条都是实际做过、有数字或对照的优化，连同踩过的坑一起写清。

## 1. 压缩预算必须 ≤ 模型上下文窗口（最重要的一个坑）

Harness 的上下文压缩由 `compressionBudget` 控制：超过预算就压缩、并保留最近 `retainTokens`。

**踩的坑**：把 `compressionBudget` 设成 `400000`，而当时默认模型（豆包）窗口只有 **256k** →
预算永远达不到 → **永不压缩** → 历史一直涨，每轮都在为全量历史付费。

现在的口径：

```yaml
compaction:
  isolate:
    compressionBudget: 180000   # 与模型窗口绑定，留出输出与工具余地
    retainTokens: 6000          # 保留近期状态与工具调用边界
```

并且**连接器会在切换模型时按窗口重算预算**（取当前可用模型窗口的最小值再留余量），
避免"换了个小窗口模型，预算还是旧的"这种隐性事故。
换模型后如果预算没跟着走，等于把上面那个坑重新踩一遍。

## 2. 关掉无关注入：系统提示词 8387 → 7153 字符

Harness 默认会注入一段"你在 Web GUI 里、有 HMR、`pnpm run dev:web`…"的**方位说明**。
本项目根本不在那个界面里跑，这段纯浪费，还会干扰人格。

```yaml
- id: web-runtime
  config:
    surfaceContext: false
```

效果：系统提示词从 **8387 → 7153 字符**（每轮都省，且不再让模型误以为"自己在开发服务器里"）。

## 3. 工具结果落盘（spill）

长输出（大文件内容、搜索命中、构建日志）不进上下文，改为**落盘 + 只回摘要与路径**：

- 模型看到的是"结果很大，存在这个路径，要不要看第几段"；
- 需要细节时再按需读——一次只读一小段；
- 好处是**上下文不再被一次性灌爆**，压缩触发次数显著下降。

预设里压缩策略只做 `group` + `isolate` + `spill-policy` 调参，不写死业务逻辑。

## 4. 记忆不塞上下文，改成"按需查"

长期记忆（时间线 / 图谱）如果每次对话都全量注入，成本会随记录增长线性上涨。
本项目的做法是**把记忆做成工具**：

| 工具 | 什么时候用 |
|---|---|
| `timeline_days` | 先看"有哪几天"，再决定要不要深入 |
| `timeline_search` | 按关键词定位到某天，而不是把整月记录读一遍 |
| `timeline_read` | 只读需要的那天/那几条 |
| `relation_query` | 只取某个人的一圈关系或两人的链路（默认 2 跳） |
| `bridge_results` | 只取停放的外部任务结果里需要的那一屏 |

**先窄后深**：先用"目录/搜索"把范围缩到最小，再读原文。

## 5. 本地模型分块小调用（省 token 也省显存）

图谱抽取不做"一次读一大段"，而是：

- 按 **~2.5k 字符**切块，每块单独调用 → 输入永远短；
- 每次带一份**很小的候选名单**（最近提到的人 + 图谱已有的人，几十个 token），
  把"那个人是谁"从"自由回忆"变成"选择题"；
- 上一块末尾几行 + 未解开的指代片段带入下一块（有界续接），跨块指代也能接上；
- 逐节点审核时，只喂**与这个人有关的事实**（几十到几百 token），代价不随图谱规模线性膨胀。

时间不敏感的任务（摘要、图谱）都在**空闲 3 小时后**才跑，用本地模型，不花云端额度。

## 6. 入站合并：3 条消息 → 1 次调用

同一人连发多条，默认攒 **6 秒**合并成一条（`DSH_WEIXIN_COALESCE_MS=6000`）：

- 省的是"每次调用都要带完整系统提示词 + 历史"的固定开销；
- 也避免模型对半句话先回一条、再对后半句回一条（那更贵）；
- 控制命令与纯媒体不缓冲，保证响应及时。

## 7. 上下文清空走 epoch，而不是"继续带着"

"清空上下文"如果只是标记一下，旧历史还会被后续请求带回来。
本项目改成：**递增 context epoch + 销毁 agent + 删除该会话的会话文件**，
下次请求拿到的是全新的会话 id。清空是真的清空，不会留下隐性成本。

## 8. 让便宜/免费的通道干重活

| 任务 | 通道 |
|---|---|
| 对话（要人格、要质量） | 云端模型（豆包 / 千问，可配故障转移） |
| 摘要、图谱抽取、图片描述 | 本地 Gemma（0 额度、0 联网） |
| 阶段性进度提示 | 只推**中文**短句（避免把英文思维链推给用户，也省 token） |

故障转移也顺手做了成本保护：额度类错误（quota）冷却 1 小时、限流（rate_limit）3 分钟、鉴权（auth）24 小时，
不会在额度用完时无脑重试烧调用。

## 9. 效果自检（怎么知道优化还在生效）

- `runtime/llm-probe.log` 里每条 `kind:"event", type:"done"` 都带 usage，可以直接看每轮 token；
- 控制台有 **Token 用量**页与 **上下文长度/压缩**卡片（能看到当前预算是否与模型窗口匹配）；
- 时间线/图谱的调度日志（probe 事件）能确认"是否真的只在空闲时跑"。
